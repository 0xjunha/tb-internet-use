# Outside knowledge

Facts that no trajectory holds, e.g. that the Codex tool `exec_command` runs a shell command. They are written by hand, never by a script, and a `reviewed` cell beside each fact says whether a person has reviewed it. A step asks for them only through its door, one class per step, which its entry function takes as an argument.

Every door guarantees three things:

- An answer is a value or an unknown, never a default.
- Each unknown input is counted, except an output line that no pattern fits, which has no name to count it under, and an argument of a tool call without a row of `harness_tool_arguments.csv`, which the door never looks up, so it fills no field without a count.
- Each use of a fact is counted.

A door reads a CSV only through `Catalog` in [catalog.py](catalog.py), whose `lookup` records the use or the miss itself. The counts depend on the dataset, so each run writes them under `out/` and no script writes a catalog.

Knowledge that a CSV cannot hold, e.g. a result format with a template and a function that builds the tool output text, is declared in Python under [declarations/](declarations/). A step reaches it through its door too, and imports no module of `knowledge/` when it runs. Since a Python line has no columns for a review, a hand-filled `<what one row is>_reviews.csv` beside the Python files records what each declared fact was checked against and whether a person reviewed it, e.g. [harness_result_format_reviews.csv](declarations/tool_call/harness_result_formats/README.md#review-record).

The columns of the CSVs are described beside them, those of `tool_call/` in the [harness tool catalog](catalogs/tool_call/README.md), those of `expanded_tool_call/` in the [program catalog](catalogs/expanded_tool_call/README.md), those of `network_request/` in the [program request catalog](catalogs/network_request/README.md), those of `network_request_result/` in the [program output catalogs](catalogs/network_request_result/README.md) and those of `export/` in the [export catalog](catalogs/export/README.md).

A declared result format is counted like a catalog row. `ToolCallKnowledge.harness_result_format` counts the format a result matched as a use of the row `(harness, tool, format)`, and a result that matched none as an unknown input `(harness, tool, unknown_format)` or `(harness, tool, skipped_format)`, both under the source name `harness_result_formats`. The key of a message that the harness wrote, which `HarnessToolCall.is_harness_message` marks, ends with `is_harness_message`, e.g. `(antigravity-cli, SYSTEM_MESSAGE, unknown_format, is_harness_message)` for the prompt of a `schedule` timer, so that it is not taken for a tool result to declare.

Output line patterns are declared in Python too, since a table is ordered and the first pattern that matches a line gives its meaning, and patterns share parts such as the regex of a host name. [output_line_pattern_declaration.py](output_line_pattern_declaration.py) holds the types, [program_output.py](declarations/network_request_result/output_line_patterns/program_output.py) the patterns read in program output and [web_tool_result.py](declarations/network_request_result/output_line_patterns/web_tool_result.py) those read in the result of a call made only of web tool actions. `NetworkRequestResultKnowledge.output_line_meaning` counts the pattern that matched a line as a use of the row `(table, pattern)` under the source name `output_line_patterns`. A line that matched none gives `UnknownOutputLineMeaning` and is not counted, since an output line has no name, so a missing pattern cannot be noticed the way a missing catalog row can. `decide_network_request_results` counts each line that a pattern fits and that gives no evidence by its reason. Under the reason `no_unknown_run` it also counts the line by the last program of each command whose output reaches its place, e.g. echo and ls for a line in the result of `echo hi; ls` and ls alone for `sudo ls`, and under `unowned_line_in_unknown_run` by that of each such command whose run is unknown, e.g. bash of `bash setup.sh` when no call of the trial wrote setup.sh. `output_line_pattern_reviews.csv` in the same folder is the review record, one hand-filled row per pattern in the order of the tables, and a test fails when its rows and the declared patterns do not pair up in that order.

## Adding a fact

1. Run the pipeline on the trials, `nice -n 10 uv run python -I scripts/run_pipeline.py <raw_trials_dir>`, or the audit script of one step, e.g. `scripts/audit_tool_call_knowledge.py` for `convert_tool_calls`.
2. Read `unknown_inputs.csv` of the step from the top, e.g. `out/pipeline/tool_call/unknown_inputs.csv`. The inputs that the most trials asked for come first.
3. Add a row for the input to the catalog by hand, as the README beside the catalog describes its columns. A harness tool that touches the task environment gets the `ToolCallAction` type for what it does, e.g. `SearchFilesAction` for a grep tool, and a tool that only handles the harness's own state gets `OtherAction`. `harness_tool_arguments_in_data.csv` of `audit_tool_call_knowledge.py` lists the arguments of the tool and their value types, to choose which fill an action field.
4. Write in `checked_against` what the fact was checked against, e.g. a section of a manual or `8 sampled tool calls in the trajectories (terminal-bench 4.1, 2026-11-19)`. Leave `reviewed` empty until a person has reviewed the row, then write `yes`. For a declared result format, write both in its row of `harness_result_format_reviews.csv`, and for an output line pattern in its row of `output_line_pattern_reviews.csv`. Add, rename or remove that row when the format or pattern is added, renamed or removed.
5. Run `./scripts/check.sh`. A row that the step cannot use, e.g. an `action_type` that names no class, raises when the catalog is loaded.
6. Run the pipeline or the audit again. The input is gone from `unknown_inputs.csv`, and `row_uses.csv` shows how often the new row was used.
